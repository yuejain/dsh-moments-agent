# 静默自主发送实现方案

本方案基于 1.1.4 客户端 / 0.2.2 插件实现，后续随 0.2.7 / 1.1.9 演进。三级发表模式与拟人化自动发送已随版本落地；**2026-10-25 第三档自动发表在本机真机端到端跑通 1 条**（拟人化调度 → prepare → 点击发表 → OCR 核验，任务 PUBLISHED / 尝试 VERIFIED / approvalId=null），详见 `docs/audit/AUTO_PUBLISH_LIVE_1_1_9.md`。默认配置仍不产生自动发表副作用。

## 当前能力与边界

`src/runtime.ts` 中有两个独立循环：`scheduleEnabled` 控制自主创作，`HumanizeScheduler` 控制拟人化自动发送。后者约每 10 秒检查一次，可持久化计划、退避次数和错误；候选通过 `humanize-policy.ts` 后仍调用原有 `Publisher`。活跃时段、quietHours、条数、间隔、随机延迟、账号、内容哈希、暂停及 Kill Switch 都参与判断。审批模式额外校验审批有效期。Mock 测试覆盖这些约束；2026-10-25 已补 1 条真机 E2E 证据，仍不能代表任意微信版本/环境的稳定性，建议小额度运行并人工抽查。

三级模式已贯通前端、插件、Publisher、HumanizeScheduler 与桌面执行器：`PREPARE_ONLY` 只准备；`APPROVAL_REQUIRED` 需要一次性人工审批；`POLICY_AUTONOMOUS` 审核通过后可直接发表，无逐条人工审批。第三档复用审核时绑定的正文与素材哈希，不创建虚假的人工批准记录。已发表内容不重复点击；`UNCERTAIN` 必须人工核对。模式选择持久化，客户端启动时恢复并同步权限；同步失败则执行器保持仅准备。

本次联调修复了 geometry 账号缺失与插件发布预检不衔接的问题：`withVerifiedWechatAccount` 为 Publisher 与 HumanizeScheduler 提供受信桌面状态。只有微信已运行、已登录、桌面原账号为空，且 Reader/Hook 健康、前后两次身份读取一致时，才补入实时账号；不回退到静态配置。账号切换、网络失败或降级均保持空值，原发布门禁继续阻止点击。此修复需要重载 DSH 插件使新 dist 生效；2026-10-25 已在微信 4.1.10.27（150% DPI）上完成真机发表验收。

当前 EXE 关闭页面后约 60 秒退出，内置执行器随之退出。`--no-browser` 只控制启动时是否打开页面，不是一个可靠的常驻产品模式。几何驱动会置前窗口、使用鼠标与剪贴板，要求登录且解锁的交互桌面。严格意义上的无界面、锁屏发送需要另外验证受支持的发布接口，不能由现有几何驱动保证。

## 第一阶段：按选定模式自动发送（已实现，真机验证 1 条）

复用现有调度器，不增加另一条直接点击微信的发布通道。先在目标版本完成纯文字准备与一次真实人工发布验收，再由所有者显式开启。示意配置如下，必须合并进完整插件配置，不要替换整行 config：

```yaml
publishMode: APPROVAL_REQUIRED
scheduleEnabled: false
policy:
  requireApproval: true
  dailyLimit: 2
  minIntervalMinutes: 180
  quietHours: ['23:00', '08:00']
  timeZone: Asia/Singapore
  approvalTtlMinutes: 120
  humanize:
    enabled: true
    delaySeconds: [90, 900]
    activeHours: ['09:00', '22:00']
    minIntervalSeconds: 3600
    jitterSeconds: 600
    maxPublishAttempts: 2
    backoffSeconds: [60, 180]
```

EXE 无需 `--allow-publish`：在「设置 → 发表模式」应用第二或第三档即可同步权限。上例为审批后自动发送；如选择第三档，则已审核内容无需逐条批准即可进入队列。实际最小间隔取 policy 与 humanize 的较大值，这里为 180 分钟。先保持 `scheduleEnabled=false`，便于独立验收发送队列；开启自主创作后，第二档生成并请求审批，第三档生成审核通过后等待发送调度。上述两个开关彼此独立。选择模式不会自行打开创作或发送调度，但已开启的发送调度将按新模式处理现有符合条件的内容。

审批可能在等候活跃时段、最小间隔期间过期。现有逻辑应停留在待人工重新审批，不能自动延长、复制或复活已核销审批。队列界面需要明确展示下一次可发时间、审批截止时间和阻止原因；没有可行时间窗时立即提示重新安排。

## 第二阶段：同一管理员 EXE 托盘常驻

新增显式 `--background` 或设置中的常驻选项；默认仍沿用当前退出行为。用户开启后，浏览器关闭不触发服务退出；托盘提供打开管理界面、暂停、Kill Switch、退出。调度仍在 DSH，EXE 只提供执行器和界面，保持单个管理员应用进程。不把桌面自动化改成 Windows Session 0 服务。自启动应由用户明确开启并单独处理 UAC，不通过关闭 UAC 或预埋提权任务实现。

同一工作区只保留一个 EXE 实例：互斥量键由规范化 dataDir 生成，第二次启动只打开已有界面。权限由已运行客户端中的三级模式选择统一同步，不通过第二次启动的参数扩大权限。准备中、已准备或发表中禁止切换；同步期间先关闭执行器发表权限，同步成功后再开放所选模式，失败保持仅准备。配置重载、退出和异常应释放互斥量与端口。

## 第三阶段：尽量少打扰的交互桌面调度

加入只读桌面空闲探测与会话判断。用户有键鼠输入、微信处于用户编辑状态、锁屏、会话断开或已有准备任务时延后，界面显示延后原因。执行前获取单任务租约，保存必要的前台窗口信息；每个输入阶段前再次检查用户活动。如发现用户开始操作，尚未点击发表时取消并回到人工处理；已点击后只能核验，不能重发。剪贴板恢复需验证当前内容仍属于程序，避免覆盖用户刚复制的内容。

不能把长按、模拟鼠标或 OCR 随机延迟包装成“完全无感”。前台恢复也应验证原窗口仍有效，失败只记录错误，不争抢焦点。通知采用异常优先：等待中保持安静，审批即将过期、超出重试上限、账号变化和结果不确定时通知；可选择一次成功摘要。

## 第四阶段：更细的自主内容授权（后续扩展）

现有第三档已由用户的全局模式选择授权免逐条审批；这一阶段将进一步增加独立持久化的细粒度策略对象。授权记录可包含所有者、账号、允许主题/来源、禁区、可见范围、内容类型、时间窗、每日上限、有效期、版本与撤销时间。可先限制为纯文字、公开范围，不处理私聊素材或自动选图。模型输出只是候选，结构化校验与审核结果必须单独记录；越界内容退回人工处理。

生成完成后，将确切内容哈希绑定到授权策略版本，形成可审计的发布授权快照。Publisher 接收的是独立类型的“人工一次性审批”或“策略授权快照”，不能伪装为 manual_admin，也不能修改已有审批记录。发布前重新校验策略未撤销、账号未变、内容哈希未变、额度和时段仍有效。

通过数据库事务领取计划与额度，租约包含 owner、过期时间与阶段；手动发送与后台发送共享竞争规则。现有内存 busy 锁不足以代表跨实例、崩溃后的 exactly-once 语义。发表点击的外部副作用与数据库不能组成单一事务：崩溃发生在点击后、结果落盘前时必须恢复为 UNCERTAIN，宁可漏发转人工，不能盲目重试制造重复动态。

## 上线验收

1. 固定时钟、随机源与 FakeWechatDriver 回归：时间边界、审批过期、策略撤销、重复内容、并发领取、重启恢复、账号切换和 Kill Switch。
2. 故障注入：准备前/后、审批核销后、点击前/后、核验前崩溃；只有能够证明没有点击的失败才能按白名单退避。
3. 影子运行：真实读取候选和桌面状态，只输出“将于何时发送及为何阻止”，不执行准备或发表。核对调度是否符合所有者意图。
4. 当前微信版本现场验收：先只准备，再一条明确批准的真实发表，人工核对内容、范围、账号与截图。版本升级后重新执行。
5. 小额度开启第一阶段；常驻、少打扰调度与策略授权按阶段交付。各阶段有独立开关、关闭入口与审计证据，不因 UI 勾选完成而自动授权。
